# Maurice PaaS

**A single-server deployment platform built on the strengths of rootless Podman.**

Maurice (friends call it *Marik*) is a Coolify-class control panel for one powerful
bare-metal server where blockchain nodes, ClickHouse, databases and application
services live side by side. It is not a Docker workflow with a different runtime
underneath. It is built around what Podman does well: rootless isolation by Unix
user, Quadlet and systemd as the lifecycle environment, built-in auto-update with
rollback, native secrets and pods.

## 1. Goals and scope

**Goal.** A deployment control panel with the convenience of Coolify, running on a
single powerful bare-metal server (reference: 48 cores, 256 GB RAM) that hosts
blockchain nodes, ClickHouse, databases and application services together.

**Pains we are solving.**

- Hand-delivering 10–15 containers: copied configs, typos in variables and
  brackets, network and port conflicts.
- Ports that are exposed by default and have to be closed by hand.
- No link between networks; hunting for internal IPs on the server.
- Logs that silently fill the disk.
- Admin database connection strings in every service instead of a proper role model.
- Remote development: the environment must live on the server and not depend on a laptop.
- `docker.sock` access, which equals root on a host holding keys and nodes.

**Out of scope.** Multi-server clusters, Kubernetes compatibility, a marketplace
with hundreds of templates, billing, multi-tenancy for external customers.
One server, one team, several workspaces.

## 2. Principles

- **Files on disk are the source of truth for the runtime.** Quadlet units are
  generated by the panel; they can be read, diffed and applied without it. The
  panel is a convenience layer, not the only point of control.
- **Isolation by default.** Every workspace is a separate system user running
  rootless Podman. Compromising one project does not give access to the others
  or to the host.
- **Nothing is published on its own.** A service port is visible only inside the
  workspace network until an explicit checkbox is set.
- **Determinism first, AI second.** Config validation, port, reference and
  network checks are done in code. AI generates and explains but is never the
  final authority.
- **Plan / apply.** Any change proposed by an agent or an external client exists
  first as a plan that a human confirms. In prod — always.
- **Secrets do not live in files.** Values exist only in `podman secret` and the
  panel's encrypted database; units, env files and logs see names only.
- **Stateless and stateful are different things.** The data model distinguishes
  them from day one: blue-green for the former, honest restart plus backups for
  the latter.
- **Reuse first, rewrite after 1.0.** Until a stable release the core is
  assembled from existing open-source components and borrowed designs
  (see [Prior art](#9-prior-art-what-we-borrow)). Rewriting foundations only
  makes sense once there is a working version and the legacy that hurts is
  known by name.

## 3. Architecture

### 3.1 Components

| Component | Role | Technology / approach |
|---|---|---|
| **Control plane** (panel) | UI, API, data model, Quadlet generation, change planning, backup scheduler, notifications | Go or NestJS; PostgreSQL for state; UI on SolidStart/React |
| **Agent** | Executes operations in the context of a workspace user: writes units, `daemon-reload`, start/stop, access to the Podman socket | Go binary; runs as root and switches into the user via `machinectl` / `systemctl --user -M`; libpod API via `/run/user/UID/podman/podman.sock` |
| **systemd + Quadlet** | Container lifecycle, restarts, dependencies, health, auto-update with rollback | Quadlet `.container` / `.pod` / `.network` / `.volume` / `.build`; templated units such as `web@.container` |
| **Podman (rootless)** | Isolation, networks, in-workspace DNS, secrets, image builds | netavark + aardvark-dns; crun; `podman secret`; buildah |
| **Edge proxy** | Domains, TLS, routing to upstreams, graceful switch on deploy | Caddy driven via admin API; optional HAProxy on L4 in front |
| **Registry** | Stores built images by digest for dev → prod promotion | Local OCI registry (zot or distribution) |
| **Logs** | Centralised logs with rotation and rate limiting | journald (`LogDriver=journald`), read through the journal API |
| **Notifier** | Events and alerts | Telegram; subscribes to podman events and `OnFailure=` of units |
| **Backup runner** | Database dumps and upload to S3 on schedule | systemd timers + restic/rclone; `pg_dump`, `clickhouse-backup` |
| **MCP server** | Single programmatic entry point for the agent, Telegram bot, Claude Code and external clients | Thin layer over the panel API with scoped tokens |
| **LLM adapter** | Any provider via the user's own key | Vercel AI SDK or LiteLLM; tool calling |
| **Task tracker** | Tasks, cycles, roles; widgets in the UI; agent as task author | Plane (self-hosted) shipped with the platform; Jira/Linear drivers |
| **Telemetry** | Per-workspace / per-service metrics, centralised logs, event feed | VictoriaMetrics + VictoriaLogs, Vector/Alloy, cgroups exporter; charts in the Maurice UI; Grafana optional |

### 3.2 Flow

```
User / Claude Code / Telegram
        |
        v
   [UI + API + MCP] <-- tokens with scopes read / plan / apply
        |
        v
   [Control plane] -- generates Quadlet units, change plans, Caddy config
        |                         |
        v                         v
     [Agent] --machinectl--> [ws-<project>] rootless Podman + systemd --user
        |                         |- web@.service        (stateless, blue-green)
        |                         |- postgres.service    (stateful, restart)
        |                         |- <project>.network   (aardvark DNS: postgres, web, ...)
        v
   [Caddy admin API] <-- routes domain -> 127.0.0.1:<port>
        |
   [HAProxy L4, optional] <-- public IPs, PROXY protocol
```

### 3.3 Isolation and users

- A workspace is a system user `ws-<project>`: `useradd --system`, `nologin`
  shell, home on NVMe (e.g. `/srv/ws/<project>`), explicitly allocated
  subuid/subgid (65536 per workspace, ranges tracked by the panel),
  `loginctl enable-linger`.
- Services inside a workspace trust each other and share the user. A dedicated
  user `ws-<project>-<service>` is created only when the *isolate* flag is set
  (signers, parsers of untrusted input).
- Nodes and ClickHouse that need full network performance run rootful with
  `Network=host`; for them the panel only offers lifecycle management.
- Deleting a workspace: stop units → `podman system reset` as the user →
  `disable-linger` → `userdel -r` → release the subuid range.

### 3.4 Network and ports

- Every workspace has its own network; service names resolve through the
  built-in DNS. The same hostname `postgres` in different workspaces does not clash.
- Container names are unique per version (`web-a1b2c3`); the service name is a
  stable `NetworkAlias` (`web`). Everything talks via the alias.
- Publishing a port is an explicit action: host port, host IP (default
  `127.0.0.1` for the proxy), optionally `0.0.0.0`.
- Cross-workspace connectivity goes through an *access link*: the service is
  published on an internal host address, the panel shows
  `host.containers.internal:<port>` and can revoke the link.
- Multiple public IPs separate zones (admin/SSH, public services, node P2P),
  not TLS.

### 3.5 Zero-downtime deploy (stateless)

- Start `web@<new>` without the alias; with `Notify=healthy`, `systemctl start`
  returns only after the health check passes.
- Switch traffic: Caddy admin API changes the upstream; for internal traffic,
  `network connect --alias` on the new container, `disconnect` on the old. Two
  containers never hold the same alias at once.
- The old container gets `SIGTERM` and drains within `StopTimeout`. Graceful
  shutdown in applications is mandatory.
- The previous image stays in the registry; rollback is the same process in reverse.

## 4. Data model

| Entity | Key fields | Notes |
|---|---|---|
| **Workspace** | `name`, `unix_user`, `uid`, `subuid_range`, `home`, `env` (prod/dev), `cpu_slice` | Isolation and resource boundary |
| **Project** | `workspace_id`, `name`, `git_repo`, `git_key_id` | Groups services of one repository |
| **Service** | `project_id`, `name` (alias), `kind` (stateless/stateful), `image` or `build`, `template_id`, `resources`, `isolated` | `kind` selects the deploy strategy |
| **Deployment** | `service_id`, `image_digest`, `git_sha`, `status`, `started_at`, `finished_at` | Version history, rollback target |
| **Port** | `service_id`, `container_port`, `published`, `host_ip`, `host_port` | Nothing is published without `published=true` |
| **Network / Link** | `workspace_id`; link: `from_service`, `to_service`, `host_addr` | Cross-workspace links are visible and revocable |
| **Domain / Route** | `service_id`, `domain`, `public_ip`, `tls_mode`, `upstream` | Generates the Caddy config |
| **Secret** | `scope` (workspace/service), `name`, `encrypted_value`, `version` | Value goes into `podman secret` |
| **EnvVar** | `service_id`, `key`, `value` or `ref` (`{{postgres.url}}`) | References are resolved by the panel, not by a human |
| **DbUser** | `service_id` (the DB), `role` (admin/app/readonly), `secret_id` | Password rotation restarts dependents |
| **BackupJob** | `service_id`, `schedule`, `target` (S3), `retention`, `last_status` | systemd timer |
| **Token** | `scopes` (read/plan/apply), `workspace_ids`, `owner` | For API, MCP, Telegram |

## 5. Roadmap

Four stages. Each stage has a purpose, a scope, done criteria and the main
risks. Checkboxes track progress.

### Alpha — the core works

**Purpose.** Prove that panel → agent → Quadlet → rootless Podman works on a
real server and can already replace manual config copying. The UI is simple but
honest: containers, logs and network are visible. No AI, no proxy, no backups.

**Scope**

- [ ] Create / delete a workspace with the full system-user lifecycle (§3.3).
- [ ] Service from a ready image and service from a Dockerfile in a git repo
      (clone by key, `podman build`, tag by SHA).
- [ ] Quadlet generation (`.container`, `.network`, `.volume`) applied through
      the agent; the resulting unit is viewable in the UI.
- [ ] Operations: deploy, restart, stop, delete; systemd status and health view.
- [ ] journald logs in the UI filtered by service; journald limits configured.
- [ ] Workspace network with DNS by name; internal ports closed by default;
      explicit publish on `127.0.0.1` or a chosen IP.
- [ ] Secrets: entered in the UI, stored encrypted in the DB, delivered via
      `podman secret`; env vars with `{{service.field}}` references.
- [ ] Deterministic validator: env syntax, unresolved references, port
      conflicts, unknown hostnames, Quadlet generator dry-run.
- [ ] Minimal UI: workspaces → projects → services, service card, logs, action
      buttons; `podman stats` in the service card.

**Done criteria**

- [ ] Any current project comes up through the panel from scratch without SSH.
- [ ] Server reboot: every service comes back on its own (linger + systemd).
- [ ] Deleting a workspace leaves no users, files or subuid entries on the host.
- [ ] No port is reachable from outside without the explicit `published` flag.

**Main risks**

- Rootless pitfalls: subuid for system users, `XDG_RUNTIME_DIR`, socket
  permissions. Time is budgeted for debugging.
- Agent as root: minimise the surface — only the listed operations, no
  arbitrary shell.
- Temptation to build a pretty UI right away. Alpha UI is functional, nothing more.

### MVP — fit for production

**Purpose.** The critical layer is solid: domains, TLS, zero-downtime deploy,
notifications, backups. The panel fully replaces Coolify for current projects
and becomes the main operations tool.

**Scope**

- [ ] Edge proxy: Caddy driven by the panel via admin API; domain → service in
      two clicks; wildcard via DNS-01 for own domains; domain bound to a public IP.
- [ ] Blue-green deploy for stateless services (§3.5); restart mode with an
      explicit warning for stateful; rollback to the previous digest.
- [ ] Local registry; images stored and promoted by digest.
- [ ] Auto-deploy via webhook from GitHub/GitLab/Gitea; manual deploy button;
      deployment history.
- [ ] Service catalogue: Postgres, ClickHouse, Dragonfly, RabbitMQ, MinIO
      templates with parameters, generated passwords and secrets.
- [ ] Health checks in Quadlet (`HealthCmd`, `HealthOnFailure`, `Notify=healthy`).
- [ ] Telegram notifications: crashes, failed deploys, backup results, restarts.
- [ ] Backups to S3: schedule, retention, restic/rclone; `pg_dump` and
      `clickhouse-backup`; a *restore* button.
- [ ] Database users: admin / app / readonly roles for Postgres, ClickHouse,
      Dragonfly, RabbitMQ; password rotation with dependent restarts.
- [ ] Cross-workspace access links (§3.4).
- [ ] Resource limits: cpuset for prod, slices for the rest; memory limits per service.
- [ ] Telemetry: VictoriaMetrics with exporters, CPU/memory/network/disk charts
      per workspace and service, deploy markers on charts (§13).
- [ ] Panel authentication, panel roles (admin / operator / viewer), audit log.

**Done criteria**

- [ ] All production projects migrated from Coolify; Coolify switched off.
- [ ] Redeploying a stateless service under load produces no client-side errors
      given correct graceful shutdown.
- [ ] Postgres restore from an S3 backup verified on a test workspace.
- [ ] No application uses an admin database connection string.
- [ ] A service crash reaches Telegram within one minute.

**Main risks**

- Panel state vs. real systemd drifting apart (someone edited a unit by hand).
  Needs reconcile and a drift warning.
- DNS alias switching vs. connection caches in clients. Must be tested on real
  services with connection pools.
- Caddy admin API has no config persistence: the panel must be able to rebuild
  the whole config after a Caddy restart.

### Beta — the full feature set

**Purpose.** On top of a stable core: MCP, the built-in agent, remote
development and integrations. Features are integrated, exercised and adjusted;
some may be cut based on real use.

**Scope**

*MCP server and external API*

- [ ] MCP server over the panel API: read tools (workspaces, services, units,
      networks, ports, logs, deployments) and planning tools (`plan_deploy`,
      `plan_env_change`, `plan_publish_port`).
- [ ] Tokens with scopes read / plan / apply bound to workspaces. `apply` for
      prod is issued to humans only.
- [ ] Claude Code and other MCP clients connect directly to the server.

*Built-in agent*

- [ ] Chat in the panel; any provider key; model selection.
- [ ] Tools only through MCP; secret values are unreachable; repositories are
      cloned into a sandbox.
- [ ] Scenario *"study the repository and draw a deployment map"*: parse
      compose / Dockerfile / `.env.example` / monorepo graph → plan of
      services, links and ports → validator ↔ agent loop → plan for approval.
- [ ] Protection against prompt injection from repositories and logs: plan-only
      mode, explicit apply confirmation.

*Remote development*

- [ ] Dev workspace: same user mechanism, `env=dev`, own cpu slice, direct SSH
      into the user.
- [ ] Dev image (headless Ubuntu: Neovim, tmux/zellij, Claude Code, language
      toolchains, code-server, Entire) via toolbx/distrobox with a shared home
      (§10).
- [ ] Agent tool *"link to file/line"* opening code-server in the browser or VS
      Code over SSH.
- [ ] Agent session history via Entire; checkpoint linked to a deployment (§11).
- [ ] The agent may apply changes itself in dev; in prod — plan only.
- [ ] Cloudflare tunnels as a panel tool: `cloudflared` per workspace, routes
      via API; the Cloudflare token is never given to the agent.
- [ ] dev → prod promotion: one button, same image digest, prod bindings
      substituted, plan and confirmation.

*Observability and Telegram*

- [ ] Log triage: code-level filter (level, patterns, dedup) → a cheap model
      answers "is there a critical error" → alert.
- [ ] Telegram bot with voice input (STT), read-only tools via MCP, log sent as
      a file; ID allowlist; mutating actions only via a confirmation button.
- [ ] VictoriaLogs with a collector: search by workspace/service/env/version
      labels; unified workspace feed with Plane tasks (§13).

*Task tracker*

- [ ] Plane as a platform service created together with Maurice; creating a
      workspace auto-creates and links a Plane project. Tracker abstraction with
      drivers (Plane default, Jira and Linear optional).
- [ ] Agent as task author: creates, links to epics, moves statuses, creates
      sprints; the human confirms and edits.
- [ ] Workspace card widget: in progress, opened/closed this week, backlog growth.

**Done criteria**

- [ ] A new project from a repository is deployed by the agent into a dev
      workspace without manual config edits; the prod plan passes without fixes.
- [ ] A developer works for a week only in a dev workspace on the server
      (SSH + Claude Code); the laptop reboots with no consequences.
- [ ] One Telegram message yields a server status answer and the log file of
      the requested service.
- [ ] The Release feature list is frozen after Beta; the excess is cut.

**Main risks**

- An agent with apply rights in dev can still damage dev data; backups are
  needed in dev too.
- LLM cost on logs of chatty services — mandatory prefilter and limits.
- Scope creep: integrations and dashboards eat time without adding value to the core.

### Release — stabilisation

**Purpose.** Everything that survived Beta works predictably. Further work is
bugs, Podman and template updates, new features on request.

**Scope**

- [ ] Documentation: installation, security model, Quadlet generation format,
      API/MCP, disaster recovery.
- [ ] Panel and agent upgrade procedure without downtime of managed services
      (the panel is not a runtime dependency).
- [ ] Podman version compatibility matrix; tests for Podman upgrades
      (auto-update, Quadlet syntax).
- [ ] Regular catalogue template updates (Postgres, ClickHouse versions, ...)
      and dev-environment image updates.
- [ ] Core regression tests: workspace creation, deploy, blue-green,
      backup/restore, deletion.
- [ ] Release process: changelog, versioning, panel rollback plan.

**Done criteria**

- [ ] One month of operation without panel-caused incidents.
- [ ] Any host incident is recoverable from the documentation without knowing
      panel internals.
- [ ] A minor Podman upgrade passes the checklist without manual unit edits.

## 7. Open decisions and risks

| Question | Options | Decide by |
|---|---|---|
| Control plane language | Go (single binary with the agent, native libpod bindings) or NestJS (faster UI/API, shared stack with current projects) | before Alpha |
| One root agent or an agent per user | Root agent with `machinectl` is simpler; per-user agent is safer but costlier to maintain | Alpha |
| Caddy vs Traefik | Caddy via admin API is runtime-independent; Traefik is convenient with labels but ties the proxy to Podman | MVP (leaning Caddy) |
| Is HAProxy L4 needed | Only for DDoS / raw TCP traffic; otherwise an extra component | MVP, based on load |
| Rootful services (nodes, ClickHouse) | Manage through the panel as *external* units or keep outside the panel | MVP |
| Plan storage format | JSON diffs in the DB vs a git repository of generated units | MVP |
| LLM for log triage | Haiku / provider mini models / local CPU model | Beta |
| Default tracker | Plane self-hosted (chosen); Jira/Linear as external drivers | Beta |

**Systemic risks.** One server is a single point of failure for everything,
including the panel: backups of panel state and a documented manual recovery
are mandatory. Rootless Podman is less battle-tested under heavy network load
than rootful — such services stay rootful. The Quadlet-panel ecosystem is young
(Rookery, quadletman, quadlet_manager, Rivetr); nothing Coolify-grade on Quadlet
exists, so much will be built here, with those projects serving as references
for the agent and compose import.

| Layer | Choice | Why |

| Registry | zot or distribution | Light local OCI registry |

| AI | Vercel AI SDK or LiteLLM; MCP server | Any provider by key, single access path for clients |
| Dev environment | toolbx / distrobox, tmux or zellij, SSH | Mutable container with shared home, persistent sessions |

## 9. Prior art: what we borrow

The point of this section is to speed up the plan with real projects: take code
or approach, integrate a component as is, or use as a UI reference.

### 9.1 Panel-level PaaS (UX and domain model reference)

| Project | What is good | What Maurice takes |
|---|---|---|
| **Coolify** (PHP/Laravel, Docker) | Most complete domain model: projects, environments, services, domains, S3 backups, notifications, service catalogue, "magic" variables linking services | Entity structure and UX of key screens; env references; catalogue templates (compose templates converted to Quadlet) |
| **Dokploy** (TypeScript, Swarm, Traefik) | Clean TS stack (Next.js, tRPC, Drizzle), readable code, DB backups to S3, templates, monitoring | If the control plane is TS — API/UI structure reference; backup and schedule logic |
| **Komodo** (Rust + TS) | Multi-server "core + periphery agent", single API/TS client, builds and deploys | Control plane ↔ agent model; message format between them |
| **ZaneOps** (Python, Swarm, Caddy) | Caddy as a managed proxy via admin API, simple service model | Caddy config generation and full rebuild on restart |
| **Dokku** (shell, Docker) | git push → deploy, buildpacks, minimalism, plugins | Plugin system idea for integrations; buildpacks as a build option |
| **Rivetr** (Rust) | Single binary, low footprint, webhook deploys, runtime abstraction Docker/Podman | Lightweight control plane example; GitHub/GitLab/Gitea webhook handling |

### 9.2 Quadlet-native panels (systemd/Podman reference)

| Project | What is good | What Maurice takes |
|---|---|---|
| **Rookery** (Go) | Control plane + agent per rootless scope; units on disk as source of truth; import of `podman run` / compose / running containers into Quadlet with warnings | Agent architecture; compose → Quadlet converter (key for migrating off Coolify) |
| **quadletman** | Web UI for rootless Quadlet with OS-user isolation | Working with several system users from one process |
| **quadlet_manager** (Go + React) | Unit management via systemd D-Bus, xterm.js web terminal, logs | D-Bus layer instead of shelling out to `systemctl`; web terminal |
| **quadman** (TUI) | Acting as other users via sudoers with an explicit command list; events timeline; templated `web@` units | Minimal sudoers for the agent; merged podman + systemd event stream |
| **podlet** | `podman run` / compose / k8s YAML → Quadlet converter | Integrate as a library or CLI in the validator and importer |
| **cockpit-podman** | Reference use of the libpod API from the browser | API call reference for containers, logs, stats |

### 9.3 Components integrated as is

| Task | Component | Notes |
|---|---|---|
| Proxy and TLS | Caddy (admin API, on-demand TLS, DNS-01 plugins) | Not rewritten; the panel generates JSON config |
| L4 and protection | HAProxy | Added when needed; config generated |

| Dev environments | toolbx / distrobox, code-server, Coder (reference) | See §10 |

**Conclusion.** Only the control plane (data model, Quadlet generation,
plan/apply, UI) and the agent are written from scratch. Everything else is
integration or borrowing. This roughly halves the Alpha and MVP effort compared
to a fully custom core.

## 10. Remote development toolkit

A dev workspace is an ordinary workspace with `env=dev`, direct SSH into the

## 11. Agent memory and session history

**Entire** is a CLI that uses git and agent hooks to capture Claude Code, Codex,
Gemini CLI, OpenCode and other sessions, storing transcripts, prompts and
metadata on a separate branch `entire/checkpoints/v1` tied to commits. The main
branch stays clean; you can roll back to a checkpoint inside a session, resume
an old session, or review the context of a change in a PR. There is a web UI at
entire.io, but the checkpoint branch lives in your own repository, so the data
stays with you.

Younger, more "memory-like" alternatives: memgit (git-like store of facts and
checkpoints across agents, with session-start hooks), Rekal (context capture on
post-commit, "why is the code like this" queries), Lethe (self-hosted versioned
memory with review and merge). Less standardised.

**How it fits Maurice**

- Entire ships in the dev image by default; the checkpoint branch is pushed to
  the same remote or a separate private *checkpoints* repository. The panel
  stores the link as part of the project.
- A Deployment gets a *session/checkpoint* field: when deploying from a commit
  the panel shows which agent session produced it. This answers "why was it
  deployed like this" the way `git log` answers "why was it written like this".
- The panel agent reads the checkpoint branch as extra context when analysing a
  repository (decisions, what was already tried).
- Maurice's own long-term agent memory (infrastructure map, per-workspace
  decisions) lives in the panel DB and is exposed via MCP; a memgit/Lethe-grade
  memory format can be plugged in later if shared memory across agents is needed.
- Stage: Beta, together with the dev workspace.

## 12. Task tracker: Plane and decomposition discipline

The problem: one task unfolds into fifteen, those into a hundred; a week goes
into writing them out, boundaries blur, tasks are forgotten, and real time
including manual testnet checks stretches several-fold. A tool does not fix
this by itself; rules do, and the tool and the agent help keep them.

### 12.1 Why Plane

- Open source (Community Edition, self-hosted), Jira/Linear-style UI: projects,
  cycles (sprints), modules, task hierarchy, views, pages.
- Role-based access: members are added to the workspace and to specific projects
  with roles (admin, member, guest). This covers "show one person the tasks of
  one project out of fifteen".
- Plane's stack (API, worker, Postgres, Redis, MinIO) maps onto the Maurice
  catalogue as an ordinary set of services — it becomes part of the platform's
  starter kit alongside the registry, Caddy and the notifier.
- REST API and API keys for automation; for the agent, a tracker driver via
  Maurice MCP. Whether Plane ships an MCP server is to be checked during
  implementation; otherwise the driver is written over REST.
- Jira stays as an external driver for teams that already have it (via the
  Atlassian MCP); Linear likewise.

### 12.2 Link to Maurice

- One Plane workspace per Maurice instance; a Maurice workspace = a Plane
  project. Creating a workspace in Maurice creates the Plane project, base
  statuses, labels and cycles; deleting a workspace archives the project (never
  deletes).
- Inviting a person to a Maurice workspace as a *task viewer* adds them to the
  Plane project as a guest; they log in to Plane with their own account and see
  only their project.
- Widgets in the Maurice workspace card: tasks in progress, opened/closed in 7
  days, current cycle, backlog growth. Click leads into Plane.
- Deployments and tasks are linked: a deploy from a branch or commit carrying a
  task number moves it to *in review* and attaches the deployment link.
- Session history (Entire, §11) feeds the agent: from the transcript it proposes
  closing what was done and filing what was found.

### 12.3 Agent as task author

- A person says (in chat or by voice in Telegram) what they found; the agent
  files the task, links it to an epic, estimates, sets status. The person
  confirms a list instead of typing.
- The agent can: create an epic with its first layer of tasks, create and fill
  a cycle, move statuses on events (PR, deploy), tag tasks discovered along the
  way as *found during X*.
- Rights: in dev — create and move freely; delete and change estimates — only
  with confirmation.

### 12.4 Decomposition rules (built into the agent, surfaced in the UI)

| Rule | Essence | How Maurice enforces it |
|---|---|---|
| Plan in waves | Only the next layer is detailed: epic → 5–7 tasks; only the task being picked up now is spelled out. The rest is a title and one line | The agent refuses to break down subtasks of tasks not in *next* / *in progress* and suggests postponing |
| At most three levels | Epic → task → subtask. A subtask that needs its own subtasks is really a task; the epic was cut wrong | Structure validator: warning and a re-slicing suggestion |
| WIP limit | No more than 2–3 tasks *in progress* per person. New work goes to the backlog tagged *found during X* | Widget turns red when exceeded; the agent will not move a fourth task to *in progress* without confirmation |
| Time-box the unknown | Research ("poke at the testnet", "size up the contract") is a *spike* with a time limit and a result of "decision or list of questions" | Spike task type with a mandatory deadline; Telegram reminder on expiry |
| Definition of done | Every task has a *done* criterion verifiable without the author (test, manual check, dev deploy) | The agent will not close a task without a filled-in criterion |
| Overheating signal | If more tasks are opened than closed in a week, the epic gets cut or part is postponed | Weekly Telegram digest: opened/closed, fastest-growing epics |

Stage: Beta, with the dev workspace and MCP. The minimum to start: Plane in the
catalogue, auto-project per workspace, the *in progress* widget and the agent
tool *create task*. The remaining rules are switched on one at a time as usage
grows.

## 13. Telemetry: metrics, logs and the workspace timeline

What Coolify and friends lack: understanding how much each project consumes and
what changed after a deploy. Maurice gets this almost for free because the
boundaries are already drawn through systemd: a workspace is the user's cgroup
slice (`user-<UID>.slice`), a service is the unit's cgroup. The kernel already
counts CPU, memory, I/O and network for them; what remains is to collect and show.

### 13.1 Pipeline

```
Metrics: cgroups / Podman / host -> exporters -> VictoriaMetrics
         -> PromQL -> charts in the Maurice UI (Grafana optional)
Logs:    stdout -> journald -> Vector/Alloy (+labels) -> VictoriaLogs
         -> label search -> UI, AI triage
Labels:  workspace, service, env, deployment_id, image_digest
```

| Layer | Choice | Why |
|---|---|---|
| Metrics store | VictoriaMetrics (single-node) | One binary, low memory, Prometheus/PromQL and Grafana compatible |
| Exporters | node_exporter (host); cAdvisor with Podman support or systemd-exporter (unit and slice cgroups); `podman stats` via API | Per-workspace and per-service load without application changes |
| Disk | Home, volume and image sizes via `podman system df` per user; home quotas | "Who filled the disk" per workspace |
| Logs store | VictoriaLogs | One binary, label and text search, retention |
| Log collector | Vector or Grafana Alloy, one process per host | Reads journald, adds workspace/service/env/deployment labels |
| Visualisation | Charts in the Maurice UI (PromQL/LogsQL queries from the control plane); Grafana as an option for deep dives | The user stays in the panel; Grafana for engineering investigations |
| Alerts | vmalert or rules in the control plane → notifier | CPU/memory/disk thresholds per workspace, error growth in logs |

### 13.2 The workspace screen as a timeline

One time axis; the prod/dev toggle is a filter on the `env` label. Shown together:

- CPU, memory, network and disk per workspace, broken down by service.
- Vertical deploy markers (version, who triggered) over the charts — a load
  spike is tied to a specific version.
- The Plane task stream for the same period: closed, in progress, current cycle (§12).
- Errors from logs: counts by level, link to the VictoriaLogs selection.
- The service card is the same screen at the level of one unit, plus live `podman stats`.

### 13.3 By stage

- **Alpha:** `podman stats` in the service card, logs from journald.
- **MVP:** VictoriaMetrics, exporters, per-workspace and per-service charts,
  deploy markers, basic threshold alerts. Needed for prod, not for looks.
- **Beta:** VictoriaLogs with a collector and labels, unified feed with tasks;
  AI triage works on top of VictoriaLogs, not raw journald.
- **Release:** retention and disk limits for the stores, dashboard export to
  Grafana, threshold tuning.

## 14. Contributing and workflow

- Code comments, documentation and commit messages are in English.
- Commit messages: a short title, a one- or two-sentence description, then
  bullet points describing what changed at a high level. No implementation
  internals, no attribution trailers.
- Work happens in a git worktree on a task branch; the branch is pushed after
  every batch of commits, then merged into `main` and `main` is pushed. As the
  project grows, merging moves to pull requests.
- Several sessions (human or agent) may be active at once. Check
  `git worktree list` and `git branch -a` before committing or merging.
